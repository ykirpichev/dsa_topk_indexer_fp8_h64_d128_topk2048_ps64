The first two numbers are the official flashinfer-bench measurement: CUDA events are replaced by CUPTI, the L2 cache is flushed, and the reported time is the span from the first kernel start to the last kernel end across 128 contest shapes. The last two are a smaller check, described below, on five synthetic shapes. They are comparable to each other. They are an upper bound on the contest number for the same shape.

The operation

For each query in a batch, score every token of a paged FP8 KV cache and return the top 2048 physical indices.

logit[t] = scale[page, slot] * sum_h ReLU(Q[b, h] · K[page, slot]) * w[b, h]
physical id = block_table[b, t / 64] * 64 + (t % 64)

Q is [B, 64, 128] FP8 E4M3. The cache is one byte buffer per page, 8448 bytes: 8192 FP8 values (64 tokens × 128) followed by 64 FP32 scales. The scale multiplies the ReLU'd dot product; it is not folded into the matrix multiply. Unused slots of the 2048-wide output are -1.

One plan, used by all four

The sequence length decides the kernel. max_num_pages is the longest sequence in the batch, in pages of 64 tokens.

PagesWhat runsWhy
≤ 32Fast pathEvery live token is inside the top 2048, so the output is the block-table remap of 0 .. seq_len. Q, K, and the weights are never read.
33–63Stage 1, then stage 2Short enough that one tile per CTA fills the GPU.
≥ 64Stage 1, then stage 2Same math. The CUDA version switches to a warp-specialized persistent stage 1 here; the ports keep one tile per CTA.

Stage 1 scores two pages (128 tokens) per CTA. A Blackwell tcgen05 MMA multiplies the FP8 tile of K by the FP8 tile of Q into FP32 tensor memory. The epilogue applies ReLU, the per-head weight, a sum over the 64 heads, and the per-token scale, and writes an FP16 logit.

Stage 2 keeps the 2048 largest logits and remaps them through the block table. Rows at or under 2048 tokens skip the select and write the block-table ids directly.

Which kernel runs

The longest sequence in the batch, measured in pages of 64 tokens, picks the kernel. At 32 pages or fewer every live token already fits in the top 2048, so scoring is skipped.

// Stage-1 plan for a call; derivable from max_num_pages alone.
enum class Plan : uint8_t {
    FastPath     = 0,  // context fits in top-K: skip Stage 1 and Stage 2
    Short        = 1,  // kFastPathMaxPages < pages < kPersistentPageThreshold
    PersistentWs = 2,  // pages >= kPersistentPageThreshold
};

inline Plan select_plan(int max_num_pages) {
    if (max_num_pages <= kFastPathMaxPages) return Plan::FastPath;
    if (max_num_pages >= kPersistentPageThreshold) return Plan::PersistentWs;
    return Plan::Short;
}

Fast path

The output is the block-table remap of 0 .. seq_len, and -1 after that. Q, K, and the weights are never read.

__global__ __launch_bounds__(128)
void topk_fast_path_kernel(
    const int* __restrict__ seq_lens,
    const int* __restrict__ block_table,
    int max_num_pages,
    int* __restrict__ out_indices)
{
    constexpr int kInts4PerRow   = kTopK / 4;           // 512 int4 per row
    constexpr int kInt4PerThread = kInts4PerRow / 128;  // 4 int4 per thread

    const int b   = blockIdx.x;
    const int tid = threadIdx.x;

    __shared__ int smem_bt[kFastPathMaxPages];
    if (tid < kFastPathMaxPages) {
        smem_bt[tid] = (tid < max_num_pages)
            ? block_table[b * max_num_pages + tid]
            : 0;
    }

    const int seq_len = seq_lens[b];
    int4*     out4    = reinterpret_cast<int4*>(
        out_indices + static_cast<size_t>(b) * kTopK);

    __syncthreads();

#pragma unroll
    for (int s = 0; s < kInt4PerThread; ++s) {
        const int i4   = tid + s * 128;                     // 0..511
        const int base = i4 << 2;                            // 0..2044, stride 4

        const int page0 = (base + 0) >> 6;                   // / 64
        const int page1 = (base + 1) >> 6;
        const int page2 = (base + 2) >> 6;
        const int page3 = (base + 3) >> 6;
        const int slot0 = (base + 0) & 63;
        const int slot1 = (base + 1) & 63;
        const int slot2 = (base + 2) & 63;
        const int slot3 = (base + 3) & 63;

        int4 v;
        v.x = (base + 0 < seq_len) ? (smem_bt[page0] << 6) + slot0 : -1;
        v.y = (base + 1 < seq_len) ? (smem_bt[page1] << 6) + slot1 : -1;
        v.z = (base + 2 < seq_len) ? (smem_bt[page2] << 6) + slot2 : -1;
        v.w = (base + 3 < seq_len) ? (smem_bt[page3] << 6) + slot3 : -1;
        out4[i4] = v;
    }
}

@triton.jit
def _fast_path(seq_lens_ptr, bt_ptr, out_ptr, max_num_pages):
    """out[b] = block-table transform of [0, seq_len), -1 past seq_len."""
    b = tl.program_id(0)
    seq_len = tl.load(seq_lens_ptr + b)
    p = tl.arange(0, FAST_PATH_MAX_PAGES)
    j = tl.arange(0, PAGE)
    # One load per page, not per token: [32] page ids broadcast to [32, 64].
    page = tl.load(bt_ptr + b * max_num_pages + p, mask=p < max_num_pages, other=0)
    tok = p[:, None] * PAGE + j[None, :]
    phys = page[:, None] * PAGE + j[None, :]
    tl.store(out_ptr + b * TOPK + tok, tl.where(tok < seq_len, phys, -1))

@tilelang.jit(target="cuda", pass_configs=_PASS)
def _fast_path(seq_lens, block_table, out):
    """out[b] = block-table transform of [0, seq_len), -1 past seq_len."""
    B = T.dynamic("B")
    max_pages = T.dynamic("max_pages")
    seq_lens: T.Tensor((B,), T.int32)
    block_table: T.Tensor((B, max_pages), T.int32)
    out: T.Tensor((B, TOPK), T.int32)

    with T.Kernel(B, threads=256) as b:
        seq = seq_lens[b]
        for n in T.Parallel(TOPK):
            # seq_len never reaches a page the table does not hold.
            page = block_table[b, T.min(n // PAGE, max_pages - 1)]
            phys = page * PAGE + n % PAGE
            out[b, n] = T.if_then_else(n < seq, phys, -1)

solution/tilelang/solution.py, lines 45–60

__global__ void fast_path(const int* __restrict__ seq_lens,
                          const int* __restrict__ block_table,
                          int* __restrict__ out,
                          int max_pages) {
    const int b = blockIdx.x;
    const int seq = seq_lens[b];
    for (int n = threadIdx.x; n < kTopK; n += blockDim.x) {
        const int page = block_table[b * max_pages + min(n / kPage, max_pages - 1)];
        out[b * kTopK + n] = (n < seq) ? page * kPage + (n % kPage) : -1;
    }
}

ReLU, the head weight, and the scale

One logit per token: the scale for that token times the sum over the 64 heads of ReLU(dot) times the head weight. Tokens past the sequence length are left out of the select.

@triton.jit
def _select_digit(digit, mask, need, BINS: tl.constexpr):
    """One radix-select round over the keys under `mask`.

    Returns the digit of the need-th largest key and the number of keys whose
    digit is larger.
    """
    hist = tl.histogram(digit, BINS, mask=mask)
    at_or_above = tl.cumsum(hist, 0, reverse=True)       # keys with digit >= bin
    # Bins [0, d] are exactly the ones that still have `need` keys at or above
    # them. One sum gives both answers: how many such bins (high bits) and how
    # many keys sit in the bins above d (low bits, always below `need`).
    packed = tl.sum(tl.where(at_or_above >= need, 1 << 20, hist), axis=0)
    return (packed >> 20) - 1, packed & 0xFFFFF


@triton.jit
def _stage2_topk(logit_bits_ptr, seq_lens_ptr, bt_ptr, out_ptr,
                 row_stride, max_num_pages, BLOCK: tl.constexpr):
    """Top-2048 of row b's logits as physical slot ids. One program per row.

    Radix select on the FP16 bit patterns, then a prefix-sum compaction; BLOCK
    is a power of two covering the whole row.
    """
    b = tl.program_id(0)
    seq_len = tl.load(seq_lens_ptr + b)
    row_bt = bt_ptr + b * max_num_pages
    row_out = out_ptr + b * TOPK

    # Whole row is inside top-K: same transform as the fast path.
    if seq_len <= TOPK:
        n = tl.arange(0, TOPK)
        keep = n < seq_len
        page = tl.load(row_bt + n // PAGE, mask=keep, other=0)
        tl.store(row_out + n, tl.where(keep, page * PAGE + n % PAGE, -1))
        return

    i = tl.arange(0, BLOCK)
    valid = i < seq_len
    bits = tl.load(logit_bits_ptr + b * row_stride + i, mask=valid, other=0)
    bits = bits.to(tl.int32) & 0xFFFF
    # FP16 bits reordered so integer order matches float order: positives move
    # above 0x8000, negatives are mirrored below it. Slots past seq_len get -1,
    # below every real key.
    key = tl.where(valid, tl.where(bits >= 0x8000, 0xFFFF - bits, bits + 0x8000), -1)

    # K-th largest key by radix select, 5 + 5 + 6 bits from the top. Triton
    # 3.7 lowers tl.histogram to one warp ballot per bin-index bit per key, so
    # three narrow rounds cost less than the two 8-bit rounds of the CUDA
    # version. `above` counts the keys strictly beyond the pivot.
    d, above = _select_digit(key >> 11, valid, TOPK, 32)
    pivot = d << 11
    d, more = _select_digit((key >> 6) & 31, (key >> 11) == d, TOPK - above, 32)
    above += more
    pivot = pivot | (d << 6)
    d, more = _select_digit(key & 63, (key >> 6) == (pivot >> 6), TOPK - above, 64)
    above += more
    pivot = pivot | d

TileLang

Import solution.tilelang.solution and call kernel. The fast path and the stage-1-plus-stage-2 path are both captured in a CUDA graph, keyed on the tensor pointers, so a replay is two graph launches. T.gemm lowers to the same tcgen05 MMA. The gather is the part that stays in scalar code: a 16-byte load comes back as a vector the frontend cannot index, and a raw shared store of that vector would skip the swizzle the MMA reads, so each token is four 4-byte loads stored one FP8 value at a time.

ThunderKittens

Import solution.tk.solution and call kernel. The loader JIT-compiles indexer.cu with -DKITTENS_SM100, TORCH_CUDA_ARCH_LIST=10.0a, and include paths /opt/ThunderKittens/include and /opt/ThunderKittens/prototype. Clone ThunderKittens there first. Stage 1 is kittens::mm_ABt: one warp provisions tensor memory, one thread issues the MMA, and the CTA reduces the 64 heads. The paged gather is a 16-byte load stored at idx ^ ((idx >> 3) & 7), which is the swizzle the TK descriptor reads. Stage 2 is the CUDA select: 1024 threads, two 8-bit radix passes, an ordered-key cache of 16384 logits.

What the gap is made of

On the fast path every version does the same block-table remap. A few microseconds there is the launch, and the TileLang fast-path smoke (15.4 µs) is that overhead on a two-kernel graph, not the remap itself. The scoring rows are where the implementations diverge.

ThunderKittens is the closer of the two ports. The MMA and the select match the CUDA kernel: 16-byte swizzled stores, one mm_ABt per two pages, and the 1024-thread 8-bit radix. The remaining gap on batch 16 (17.5 µs against a 13 µs contest row, 24.4 µs against 18 µs) is the epilogue, which round-trips the accumulator through shared memory before the head reduction, and the event timer, which counts the gap between the two launches. This port does not capture a CUDA graph.

TileLang pays for the gather and for a smaller stage 2. Four-byte loads plus scalar shared stores move the KV tile much more slowly than the 16-byte swizzled store, and the select is a 512-thread 5+5+6 radix whose histograms and scans live in shared memory. That is why 28.5 µs and 44.0 µs sit well above the other three on the same shapes. The first draft was several times slower still: a shared atomic per head, a K-dimension split into four MMA steps, and a persistent loop that left most of the GPU idle. One tile per CTA, one GEMM, and a warp reduction removed that.

Triton 3.9 is the fastest of the four on the contest harness. The source is the same plan, and the compiler version is the difference: 3.7 is 8.18 µs mean, 3.9 is 6.78 µs, with the gain concentrated in stage 2.
